# FRD: Stale extension ctx fix

## Summary
The router extension intermittently throws pi's own error — "This extension ctx is stale after session replacement or reload" — to end users. Root cause: captured `ctx` objects are used **after an `await` gap** while pi has already invalidated the extension runtime because a session replacement or reload landed mid-gap. The fix centralizes ctx access behind one guarded accessor that returns the freshest captured ctx and swallows only pi's stale-ctx error, applied uniformly to every post-await ctx action across event handlers, commands, and the provider stream path — with the model stream itself left untouched.

## Problem & Intent
End users of the router run pi with this extension and occasionally see:

> Error: This extension ctx is stale after session replacement or reload. Do not use a captured pi or command ctx after ctx.newSession(), ctx.fork(), ctx.switchSession(), or ctx.reload().

The developer's framing (verbatim): *"End users of the router"* experience it. Success is defined as *"no error during normal sessions, reloads, or session switches."* The error is thrown by pi, not by the extension, and the desired fix is at the **root cause**, not a symptom patch.

Probe evidence pinpoints the mechanism: pi's `AgentSession.dispose()` calls `extensionRunner.invalidate(...)` (`@earendil-works/pi-coding-agent/dist/core/agent-session.js`), which permanently sets `staleMessage` on the extension runtime; every later access through a captured ctx hits `assertActive()` and throws exactly this message (`dist/core/extensions/loader.js`). The extension holds a captured `lastExtensionContext` (refreshed only on `before_provider_request`, `extensions/index.ts:527-529`) and passes `ctx` params into async handlers that use them after awaits — so a session replacement/reload landing inside any of those gaps leaves a dead ctx in hand.

## Goals
- Eliminate the stale-ctx error from every path: event handlers (`index.ts:536, 572, 584`), command sub-handlers (`commands.ts:224, 411-417, 684`), and the provider stream path (`provider.ts:466, 589-593, 703, 726`).
- Close the mid-stream staleness window: no captured ctx used after the classifier roundtrip (`provider.ts:334`) or the delegated `for await` stream (`provider.ts:636`).
- Keep the existing defensive guards (`captureCtx`, `persistState`, `restoreStateFromSession` wrapper) and harden the unguarded throw surfaces: `ui.ts:111-121` (`updateStatus`) and `recordDebugDecision` (`index.ts:114-130`).
- Preserve router state continuity: pins, profile, budget restored on `session_start` via `restoreStateFromSessionInner` (`index.ts:343-438`) keep working.
- Extension-first: no change to pi core.

## Non-Goals
- No modification of pi core — the error is thrown by pi's own `assertActive()`; the fix lives entirely inside the extension.
- No change to routing decisions, tier selection, or model delegation behavior.
- No new persistence/state mechanism beyond the existing `router-state` session entries.
- No restructure around `withSession` callbacks (evaluated as an alternative approach, rejected in favor of the central guarded accessor).
- No aborting of in-flight model requests when staleness is detected (the stream continues).

## Functional Requirements
1. The extension SHALL expose a single guarded accessor that returns the freshest captured ctx and executes ctx-touching actions such that a stale-ctx error never escapes to the caller.
2. The accessor SHALL classify staleness by matching pi's error message text (`"ctx is stale after session"`); any other error SHALL propagate unchanged.
3. All ctx actions that can run after an `await` SHALL route through the accessor: UI updates (`setStatus`, `setWidget`, `setHiddenThinkingLabel`), notifications (`ui.notify`), and registry/session reads on the provider path.
4. In the provider stream path, when staleness is detected after the classifier roundtrip (`provider.ts:334`) or during the delegated stream (`provider.ts:636`), the extension SHALL skip only the cosmetic UI update (status line / thinking label) and SHALL NOT abort or alter the model request or its output.
5. `updateStatus` (`extensions/ui.ts:111-121`) SHALL not throw when handed a stale ctx.
6. `recordDebugDecision` (`extensions/index.ts:114-130`) SHALL not throw when `lastExtensionContext` is stale.
7. Router state continuity SHALL be preserved: `restoreStateFromSessionInner` (`extensions/index.ts:343-438`) still restores pins/profile/budget on `session_start`.

## Non-Functional Requirements
- **Performance**: the guard adds no measurable latency — a try/catch around cosmetic UI calls only, never on the model path.
- **Security**: none — no auth, data, or threat-model surface changes.
- **UX / Accessibility**: after a session switch, the old session's status line / thinking label may stop updating (it is skipped); the new session renders its own UI from fresh events. Acceptable by design.
- **Reliability**: the stale-ctx error must never surface to the user from any path; the model stream must not be disrupted by the suppression.

## Constraints & Assumptions
- Extension-first mandate (project AGENTS.md): all functionality lives in the extension; pi core is untouched.
- The extension never triggers session replacement itself — no `ctx.reload()`/`newSession`/`fork`/`switchSession` calls exist in `extensions/` (grep-verified). Invalidation is always external, so the fix must be defensive.
- `before_provider_request` is the contract anchor: pi emits it with a fresh ctx immediately before each provider request, and it fires across session replacements (`extensions/index.ts:521-529`). The accessor relies on this to eventually refresh `lastExtensionContext`.
- Assumption (to verify in research): pi's stale-ctx error message string is stable across pi versions — the message-match classification couples to it.
- Assumption (to verify in research): the extension closure (module scope inside `routerExtension`, `index.ts:38-54`) survives session replacement and keeps receiving fresh events; if pi instead re-instantiates the extension, the accessor design still holds but capture continuity differs.
- Existing test suite (`npm test`) must stay green.

## Acceptance Criteria
- [ ] Running `npm test` exits 0 with new unit tests that hand `updateStatus`, `recordDebugDecision`, and the provider UI path a ctx mock whose getters throw pi's stale-ctx error, and assert no exception escapes.
- [ ] Manual repro: run pi with the router extension, start a long model request, trigger a session switch (e.g. `/new` or fork) mid-request, and confirm no "ctx is stale" error appears in output or logs.
- [ ] No regression: routing decisions and model delegation behave identically when no session replacement occurs (existing tests + one manual smoke run).
- [ ] State continuity: after a session switch, `/router status` still shows the pinned profile and tier from before the switch.

## Recommended Approach
A central guarded ctx accessor in `extensions/index.ts`, built on the existing `captureCtx` pattern: one `withFreshCtx(action)`-style helper returns the freshest captured ctx and executes the action under a guard that catches and swallows only pi's stale-ctx error (message match), applied uniformly to all post-await ctx actions in the `index.ts` event handlers, the `commands.ts` sub-handlers, and the `provider.ts` UI updates. The provider's model stream and routing logic are untouched; only cosmetic ctx-touching calls route through the guard.

### D6 — Recommended approach (shape)
**Question**: How should the fix be shaped? Tradeoff axis: root-cause correctness (never hold a ctx across an await) vs minimal change (guard the throw sites) vs contract alignment (use pi's `withSession` for post-replacement work).
**Recommended**: Central guarded accessor — one accessor returns the freshest ctx and guards every ctx-touching action, swallowing only the stale-ctx error. Optimizes correctness + closes the stale window, costs a medium refactor across `provider.ts`, `commands.ts`, and the event handlers.
**Chosen**: Central guarded accessor.
**Rationale**: extends the existing `captureCtx` pattern (D4), closes the window (D3), and keeps routing behavior untouched.

### D7 — Stale classification
**Question**: The accessor guards every ctx-touching action. How should it classify "stale" so it swallows only the stale-ctx error and lets real errors surface?

**Rationale**: precise — real bugs still surface; accepted coupling to pi's message string (recorded as an assumption).

### D8 — Provider path behavior when stale mid-stream
**Question**: In the provider stream path (the minutes-long stale window), what should happen when staleness is detected mid-stream?
**Recommended**: Skip UI update, keep stream.
**Chosen**: Skip UI update, keep stream.

### D9 — Guard scope
**Question**: Which ctx actions should route through the guarded accessor?
**Recommended**: All post-await ctx actions.
**Chosen**: All post-await ctx actions.
**Rationale**: uniform rule with no per-site reasoning; the next added ctx use cannot silently reintroduce the bug.
